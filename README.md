# METAINTELIGENCIA DOMAIN

## Propósito

Dominio del Commercial Operating System (COS) dedicado a gobernar la evolución de su inteligencia: conocimiento, genealogía, patrones, aprendizaje, supersession, reutilización y baselines de inteligencia.

Este dominio controla **la versión de la inteligencia**, no solamente la versión del software.

## Posición dentro del COS

`METAINTELIGENCIA DOMAIN` pertenece al nivel de **Metainteligencia**.

Su función es observar cómo aprende y evoluciona el COS, mientras los dominios operativos aprenden sobre el negocio.

```text
DOMAIN LEARNING
      ↓
conocimiento del negocio
      ↓
METAINTELIGENCIA DOMAIN
      ↓
conocimiento sobre cómo aprende y evoluciona el COS
      ↓
EVO
      ↓
NEW INTELLIGENCE BASELINE
```

## Relación con el Curator

El dominio consume y organiza el conocimiento producido por las herramientas del Curator, incluyendo:

- Cold Entry / Rehydration
- Drills
- CCAMEL 360
- Classifier
- Reconciliation
- Evidence / Checkpoints

El **Classifier** funciona como memoria de profundidad de los drills: registra hasta qué punto un objeto ya fue investigado, qué fue reutilizado, transformado, rescatado o descartado y cuál es la frontera aún no resuelta.

## Relación con EVO

Este dominio **no crea una segunda EVO**.

EVO sigue siendo el mecanismo constitucional de evolución del COS. Metainteligencia organiza el conocimiento que permite que EVO opere sobre una base histórica y evolutiva verificable.

```text
HISTORIA / EVIDENCIA
        ↓
GENEALOGÍA
        ↓
CLASIFICACIÓN
        ↓
SUPERSESSION
        ↓
FUTURE RELEVANCE
        ↓
EVO
        ↓
TO-BE
        ↓
AUTORIZACIÓN
        ↓
MATERIALIZACIÓN
        ↓
EVIDENCIA
        ↓
NUEVA BASELINE
```

## Soberanía

`atlas-cos-v1` permanece como fuente canónica de verdad constitucional y doctrinal.

Este dominio no puede redefinir por sí mismo la Constitución, la autoridad directorial, el OVR global, CEND ni EVO. Su función es producir y gobernar conocimiento evolutivo para que las decisiones futuras puedan ser trazables y verificables.

## Regla de reutilización

La necesidad TO-BE no obliga a crear arquitectura nueva.

```text
TO-BE / NECESIDAD
        ↓
¿YA EXISTE COMPONENTE?
   ├── SÍ → REUSE
   ├── PARCIAL → TRANSFORM
   ├── HISTÓRICO RECUPERABLE → KNOWLEDGE-RESCUE
   └── NO → DELTA / GAP
```

Solo después de demostrar que el componente existente no puede satisfacer la necesidad se justifica una nueva materialización.
